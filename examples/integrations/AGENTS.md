# Char 能力插件开发指令

根据当前需求接入软件，交付独立、可导入的 `.charintegration` 和可维护源码。目标软件、CLI/Desktop、终端和能力由用户需求决定。用户只需提目标，你负责查证、开发、基本验收和交付；真实客户端与 Char 界面的验收默认由用户操作。

## 执行顺序

### 1. 建立工作区并跑通骨架

先读 SDK 根的 **`docs/plugin-development.md`**。本文件上两级目录为 SDK 根，包含 `Package.swift` 和 `scripts/new-capability-plugin.py`；独立项目使用用户给出的 SDK 路径。默认工作区 `integrations/<软件slug>/`，用户指定目录时在该目录开发，Char 作为只读 SDK。继续已有文件；源码、事实、测试与生成器留在工作区，运行包输出到 `packages/`。

首轮说明工作区和拟实现能力，随即运行指南中的骨架与 hello/inspect 检查。完成条件：真实身份已查证或明确标记未知，骨架能被生产工具解码。骨架有效不等于插件完成；继续实现，不逐模块等待“继续”。

### 2. 查证本次能力所需的客户端事实

在 `facts.md` 记录版本、来源、加载入口、根/子身份、CLI/Desktop 分流、去敏原生样本、配置根与导航 API。优先官方文档/帮助，再定点查看目标客户端安装资源。已有需求/上下文可决定的能力与终端直接采用；只对无法查证且改变交付的用户选择集中提问，等待时继续独立工作。原生取证不是默认开发阶段，不为了可选探测追加环境授权。

清单查 `docs/integration-plugin-format.md`，声明方法查 `docs/capability-adapter-protocol.md`。终端 bundle 来自终端 App，Desktop bundle 来自目标 App；动态 workEnd 自行命名。这些均无需查询 Char 枚举。只有具体工具错误无法由 SDK 契约解释时，才查看对应的一处宿主源码，记录契约缺口和最小反例；宿主改动另行提出。

大文件先识别类型/大小，ASAR 用索引提取指定文件，SQLite 查必要字段，打包 JS 限定片段与输出。查到本次所需的加载结构与事件/导航契约即可进入实现，其他客户端内部接口不继续探索。完成条件：每项声称支持的能力都有来源或验证方法，未知项有明确降级；未经查证的精准能力不列为推荐选项。

### 3. 确认身份和准确图标

CLI/Desktop 分别定义唯一 id/workEnd 和 clientInterface，共用源码可生成双包；CLI 承载应用不是 Agent 身份。按 **`docs/plugin-icon-sourcing.md`** 获取图标：本地官方资源 → 网上核实的官方资源 → 请用户上传/提供路径。将确认的资源独立保存并随包交付，记录来源，打开实际图片核对。CLI 角标由宿主添加。

完成条件：两端身份、清单引用和实际图像一致；图标格式有效与身份准确分别有证据。仅在用户允许时使用标记为待确认的临时图标；等文件期间继续实现。

### 4. 实现声明的能力

先按 **`docs/plugin-performance.md`** 列出常驻进程、运行时与预算；将监控保持轻量，维护/重型依赖按需使用。按 `docs/plugin-development.md` 的分支示例及协议实现，只声明实际具备的能力：

- **monitor**：原生推送优先，结构化日志增量读取备选。保留根/子身份与真实事件时间，白名单元数据；没有结构化信号的原因列为缺口。客户端 Hook 安静、失败不阻断客户端；适配器 stdout 只输出协议。
- **visit / origin**：聚焦并确认具体对象才报告 exact+verified，只激活应用报告 fallback。没有具体起点对象时省略 origin，由宿主应用级回城接管。tmux pane 活跃不是终端窗口在前台的证明；来源 App PID 与 CLI PID 分开处理。
- **lifecycle**：inspect 只读并核对身份、版本、入口与启用证据。安装/更新可恢复；卸载按所属文件操作并保留备份、无关文件及用户自定义路径。双包共享资源由插件跨进程协调，不借用内置客户端专用提示。

路径来自宿主环境与字符串配置，模板用结构化序列化，运行时与依赖分别查证。普通请求共用3秒总预算，维护共用15秒；完整限制以协议为准。

首次/最近/关闭起点、过滤、排序、Hold、快捷键、提醒音、气泡及动画由 Char 提供。完成条件：每项声明有实际实现，精度与支持范围匹配事实。

### 5. 验证最终生成包

按 **`docs/plugin-basic-acceptance.md` 的执行策略**组织快测：先一个进程冒烟与清理，再按改动运行相关组，最后对完整生成包跑适用快测一次及每包SDK检查。共享代码只测一套机制，各端身份/路由分别检查；历史积压、子身份、文件所有权与共享恢复仍须覆盖。

原生模型/PTY框架默认留在按需检查；开发所需契约可用官方字段与去敏样本查证，实际加载/交互交给用户。只为当前证据缺口做有限探测，不反复全量重跑。按 `docs/plugin-performance.md` 的默认目标及基本验收要求做一次轻量性能采样，分别报告宿主、适配器和按需helper，CLI/Desktop记录合计；运行时基线高时做一次轻量替代对照。实现未变时复用证据。

完成条件：适用快测与各包检查通过，已知实现错误解决、进程和临时资源清理后立即交付。原生未测项明确交给用户，不追加新类别或完整原生框架来推迟交付。

### 6. 主动交付用户验收

按 **`docs/plugin-user-acceptance.md`** 填写工作区 `USER-ACCEPTANCE.md`，最终回复直接给出完整、无需终端命令的 GUI 步骤和反馈表，而非只给文件链接。将具体路径、菜单、依赖准备、加载方式、预期、恢复填好；不能让用户自行补齐模板。

分别报告“开发及基本验收完成”和“待用户真实验收”。交付源码/包、构建与测试方法、能力/信号/精度矩阵、图标来源、配置/依赖、性能与已知缺口。真实验收待完成时称待验收测试包；收到反馈后修复并记录结果。

**提供验收说明不需要打开 App、请求解锁或替用户测试。** 只有用户明确要求某项准备操作或代测时，才按已有授权执行。发布、模型请求及用户配置写入不由开发指令自动授权。两次平台恢复与开发缺陷分别记录；网络/限额中断后从现有产物继续。
