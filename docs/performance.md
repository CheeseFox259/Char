# 性能与测量范围

Char 优先使用原生事件、增量读取和原生动画。设置 → 性能可按需开启当前进程的 CPU/physical footprint 采样（RSS在详情中），展示当前、平均、峰值与有效样本数；关闭后停止采样，重置后开始新的统计窗口。默认不采集，不向网络发送统计。

## 成本归属

| 部分 | 运行方式 | 成本与边界 |
| --- | --- | --- |
| Char 宿主 | 单一进程，AppKit/SwiftUI/Core Animation | 窗口、日志解析、焦点查询、形象解码与共享渲染；不能全部归给某个插件 |
| 内置集成 | 共享宿主观察器 | 不为每个内置客户端常驻一个适配器；安装维护的 Node/Python 按需退出 |
| pi / DeepSeek 扩展 | 客户端已有运行时 | 写白名单元数据，不再每条事件启动 char-hook；不额外启动运行时 |
| Claude / Codex / Kimi Hook | 短暂原生可执行文件 | 客户端要求命令 Hook 时保留最小入口，不启动完整客户端 SDK |
| MiniMax 示例 | 每个启用工作端一个原生适配器 | CLI/Desktop 分别计费；维护/导航 Node helper 按需运行 |
| 形象脚本 | 选中形象按需启动受限执行器 | 高频动画留在宿主；脚本只接收事件、调用 Char 动作 |
| 外部开销 | 客户端、WindowServer、GPU | 不包含在 Char 的进程行中 |

CPU 用累计 user+system 时间差除以墙钟时间，100% 表示占满一个逻辑核心。RSS 包含共享映射，不等于独占物理内存，也不能把 RSS 总和称为系统实际新增 RAM。面板统计范围与归属见 [性能面板](performance-dashboard.md)。

## 运行机制

- **变化才刷新**：不变的提醒快照不重复提交桌宠/状态栏，效果队列仍排空；语言、设置、插件与主题变更显式刷新。
- **按显示尺寸解码**：形象/跟随层按绘制尺寸载入；相同图标通过内容哈希复用8位RGBA位图。软件界面图标使用36/128/256像素版本，1024原文件留给安装图标生成。避免大图交给AppKit后形成隐式高分辨率位图。
- **缓存预算与生命周期**：动画源图片16 MiB、界面图标2 MiB，按实际解码行宽×高度计费并LRU淘汰；当前循环频繁访问的帧保持热度。主题、形象、尺寸和插件变化释放失效资源；系统内存压力清理缓存，当前显示纹理仍可用。PNG完整解码校验和安装图标的临时对象使用局部生命周期。图层、AppKit和系统绘制不在此预算内；冷帧再次使用需要解码，缓存释放不保证RSS立即降低。
- **分批日志**：每文件每批最多 512 KiB，保留半行原始字节，完整后再解码。截短/轮转重置半行；启动跳过旧记录。积压分批让出 UI 执行器，全部读取完才推进提醒时钟，不把过时的中间停顿误当最终状态。单行超过 16 MiB 会跳过并输出不含正文/路径的诊断；批次限制不会丢弃正常完整事件。
- **共享解析**：Kimi 与其他内置集成共用一次 Hook 流读取；Kimi Hook 只解码一次。跳过已关闭 Kimi wire、按轮次清理审批去重缓存；复用 decoder 与固定日期 formatter，Claude/Codex 无关记录不进行日期解析。目录条目缓存沿用 inode/mtime/ctime 检查，已知文件仍检查追加，维持发现可靠性。
- **客户端直接追加**：pi/DeepSeek 在现有运行时中以单次 `O_APPEND` 写入小型元数据，写后关 fd，兼容轮转，无队列、子进程或每会话 timer。超过 16 KiB 的元数据和写失败使用一次客户端拥有的警告，不向 TUI 原始输出。同步本地 I/O 的代价是异常缓慢文件系统可能延迟客户端回调；目标是本机私有支持目录。
- **维护完整收尾**：维护适配器 EOF 后排空已接受的请求，限制 helper 输出缓冲；退出回收所属子进程。不会把低频维护变成新的常驻服务。

升级到此版本后，pi/DeepSeek 的已有客户端会话仍持有旧代码；从插件维护菜单更新所属集成，再由用户重载客户端。Kimi/Claude/Codex 的日志观察改进随 Char 更新生效，不要求改写其 Hook。

## 隔离实测

2026-10-07，Mac16,12、macOS 26.5.1、Apple Silicon，10 个逻辑 CPU。原始过程/样本本地归档，不包含用户转录，公开文档保留口径和可运行工具。

### 宿主呈现样本

v1.0.0 Release 构建、独立 bundle ID 与随机临时配置，默认方块、桌面 48 pt、20 pt 气泡距离、4 个演示气泡、插件设置可见，性能面板关闭。没有真实日志观察/焦点查询、模型请求或客户端集成安装。预热后连续 20.06 秒，宿主平均 CPU **0.073% 单核**、RSS **27.6–27.7 MiB**。

此场景仅覆盖呈现/设置的稳态成本，不是完整用户环境的占用，不与旧版本真实观察样本相减。更换形象、历史日志数量、启用适配器与权限会增加成本；用户实际配置应看性能面板。

### 内置事件写入

同一进程测试入口、同一本机临时目录、同一元数据；每模式 5 次预热、60 个事件。旧路径调用 Release 构建的原生 char-hook，新路径调用实际共享写入器。

| 工作端 | 旧进程路径中位 / p95 | 新运行时路径中位 / p95 |
| --- | ---: | ---: |
| pi | 5.40 / 6.22 ms | 0.048 / 0.073 ms |
| DeepSeek Desktop | 3.61 / 3.81 ms | 0.037 / 0.050 ms |

这是**单条本地写入**测量，不包含宿主 500 ms 观察调度、UI 动画、模型响应或客户端自身运行开销；不据此宣称整体 CPU/RSS 同比例下降。复测：`node integrations/native/benchmark.mjs /absolute/char-hook`，只写临时文件，不安装客户端、不调用模型。

### MiniMax 示例

同机隔离的原生入口约 **9.6 MiB RSS/端**、3.3 MiB physical footprint/端，空闲平均 CPU <0.01% 单核，本地追加→协议帧 p95 <2 ms。Node 参考入口约 52.9 MiB RSS，常驻 RSS 约减少 82%。按需自检 helper 总耗时约 118 ms、生命周期 RSS 高水位约 49.1 MiB。安装/导航峰值未测。方法、工具和缓存边界见 [示例说明](../examples/integrations/minimax-code/README.md)。

### 菲比分层形象的内存对比

2026-10-07，同机release、隔离demo、日光、桌面48pt、30fps、7个演示工作端；不接入真实客户端。相同工作负载：导入后读取启动计账，每阶段预热2秒、采8次（间隔1秒），依次闲置、设置打开、关闭设置并切换动作。性能面板关闭。脚本保持事件驱动。

| 阶段 | 优化前footprint | 优化后footprint | 前/后CPU（单核） |
| --- | ---: | ---: | ---: |
| 闲置均值 | 57.00 MiB | 30.08 MiB | 0.262% / 0.249% |
| 设置打开均值 | 88.75 MiB | 56.26 MiB | 0.300% / 0.316% |
| 动作切换均值 | 84.18 MiB | 52.07 MiB | 0.319% / 0.327% |
| 启动阶段系统峰值 | 99.69 MiB | 31.02 MiB | — |
| 全流程系统峰值 | 99.69 MiB | 60.31 MiB | — |

峰值读取原生`ri_lifetime_max_phys_footprint`，不同于面板开启期间的采样峰值。分配栈将旧32 MiB块定位到`refreshSkins → NSApplication._updateIconImageFromOriginal → lockFocus → NSNewBitmapBackingStore`：将1024逻辑尺寸图标设为应用图标形成隐式位图。新版设置阶段CG image区域约2.86 MiB，旧版约32.9 MiB。对象堆仍包含SwiftUI/AppKit等共享成本，未将它们全部归给形象或声称发生泄漏。

这些是同条件短时隔离测量，不是真实配置的固定占用保证；CPU未显示持续解码增长。可用release应用的`--smoke --memory-check`复测，环境变量`CHAR_APPEARANCE_CHECK_PACKAGE`和`CHAR_APPEARANCE_CHECK_OUTPUT`均为绝对路径。该入口仅使用临时配置、演示事件和本地资源，不安装客户端集成或同步正式图标。

## 验证与后续优化

版本门禁检查事件格式与 Swift 分类器等价、混合并发完整追加、半行/UTF-8/轮转、禁用/重新启用基线、完整积压后的状态，以及缓存预算/重载和不变状态不刷新。真实模型触发与具体客户端 GUI 行为由用户验收；本轮未替用户发起请求。

减少扫描可进一步采用文件事件提示、焦点事件订阅；需要保留遗漏事件的补扫与轮转发现。降低动画帧率可以省资源，但会影响流畅度；不作为默认优化。长时内存、GPU/WindowServer、电池功耗和所有插件组合没有统一基准，不能把短时单机场景推广为固定占用保证。插件作者使用 [性能开发契约](plugin-performance.md)。
